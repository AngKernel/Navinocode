## 仍需处理的风险

### 1. 状态有两份权威来源

`Index.jsx` 持有独立 React state 并直接读写 `apps/todos/...`，`advanced/storage.js` 又维护整份工作区状态并双向投影。多个组件各自加载、保存和监听；命令和工作区切换依赖 reload。局部修复降低了误写风险，但不同标签页/旧组件状态仍可能覆盖新数据。

建议以工作区 state 为唯一业务状态，React 通过 Context + reducer 或 `useSyncExternalStore` 订阅；localStorage/extension storage 只做持久化适配器，legacy keys 只用于迁移与短期兼容。首先统一 todos/apps/settings 的读写入口，不要先把一个大页面机械拆成几十个小文件。

### 2. 合并协议不能正确表达所有删除，也没有分布式 CAS

`mergeEntityArrays` 和 folder appIds 主要是取并集，所以旧设备可能恢复已删除实体/成员。PR #3 的 tombstone 方案是相关工作，但该 PR 的说明仅覆盖工作区、文件夹和根应用；待办删除、成员移动和删除标记回收仍需单独验证。

Supabase 的 `readRemote -> revision + 1 -> upsert` 不是比较后原子写入：两设备可以同时读取相同 revision 并覆盖彼此。需要数据库函数或带旧 revision 条件的更新，冲突后重读重试。base revision 的存储键还应包含后端 URL、表名及同步 ID。

本次原生同步队列仅限单页面，不是跨标签页锁；分块校验也不是分布式事务或完整内容哈希校验。下一阶段应使用 generation/content hash、写入协调者或跨页锁，以及按实体版本/删除标记制定合并语义。

### 3. 主页面数据入口尚不统一

基线 `Index.jsx` 的 todos/componentSettings 初始化直接 JSON.parse，损坏 JSON 可使页面异常；apps 初始化把空数组当作没有配置而恢复默认应用；背景亮度初始化使用 `parseInt(...) || 100`，显式 0 无法保留。本次修复的是工作区层读取，不应把这些主页面路径标记为已修复。建议统一 schema 校验和默认值后一起修正，并加页面级测试。

`applyFullSnapshot` 的预校验不等于对浏览器 quota/security 异常具有事务回滚。未来应先校验完整 payload，再以单一版本化记录写入，必要时保留上一有效版本。

### 4. 构建与维护基线

存在声明但不可运行的 lint、缺少锁文件、Node 18 配置和宽松依赖范围。建议单独升级受支持的 Node 版本、提交锁文件，建立 lint/单测/构建/扩展校验四道检查；避免在修复业务逻辑时一起盲目升级依赖。

## 建议架构边界

```text
UI（主页 / 命令中心 / 工作区管理）
                 ↓ actions / selectors
WorkspaceStore（唯一业务状态 + 版本迁移）
         ↙                       ↘
PersistenceAdapter             SyncCoordinator
Web / Extension / AssetStore   Browser / Supabase adapters
```

保留现有 React/Vite/Radix 技术栈。图片二进制与轻量业务配置分离，配置只持有资源引用；不同同步后端复用同一套快照、校验和冲突语义。schema 迁移用显式纯函数，不在组件 render/useMemo 中读写持久化数据。
