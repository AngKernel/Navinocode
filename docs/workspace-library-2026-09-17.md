# 工作区与网站整理：统一模型、减少重复入口

## 交付范围

整合基线是 `main@a2c42cb` + PR #4 (`dd03edb`)。本分支保留 #4 的命令与同步修复，重新实现 PR #3 的层级方向及 v3/v4 迁移，并将状态提升为唯一来源；不直接叠加两个互相修改同一模块的 PR。主分支、Supabase 表结构和发布版本未修改。旧 PR #3/#4 不应与这份集成分支分别盲目合并。

## 产品职责

| 概念 | 保留的职责 | 去掉的重复 |
| --- | --- | --- |
| 工作区 | 工作/学习等场景；独立网站、待办、组件、背景与布局 | 不再承担“第二套网站分类标签”功能；新建不会隐式复制现有内容 |
| 文件夹 | 当前工作区内的单层网站目录 | 去掉多选成员列表；网站不同时出现在根目录和多个文件夹 |
| 整理网站 | 唯一编辑器，按当前目录展示网站，添加、编辑、删除、单项/批量移动 | 删除旧 AppSelector 的独立管理实现；Dock 和顶部只是同一编辑器的快捷入口 |
| 首页文件夹 | 快速展开/打开网站，链接到同一个整理面板 | 不内嵌另一套编辑流程 |
| 同步/备份 | 全局“设置 → 数据” | 从工作区管理移走，避免误解为每个工作区需单独配置账户 |

首页只有一个工作区时隐藏切换器。整理面板默认突出目录导航；新建/复制/改名等低频工作区操作折叠在“管理工作区”中。文件夹暂不支持嵌套，避免为导航产品引入复杂文件系统。

新建工作区为空白；复制是显式动作，重新生成工作区、文件夹、网站、待办 ID。解散文件夹不删除网站，而是移回未分组。删除工作区需确认且必须保留至少一个。网站及待办删除提供撤销；任何后续编辑/同步发生后，旧撤销不能覆盖新状态。

## 数据结构与写入边界

- `workspaceModel.js`：纯数据归一化、版本校验、v3/v4 目录迁移。
- `storage.js`：加载、缓存、订阅、业务操作、快照、备份恢复；一次修改只提交一个权威 JSON 记录。
- `useWorkspaceStore.js`：`useSyncExternalStore` 订阅；返回缓存快照，避免每次渲染创建新快照。
- 页面、命令中心、Dock、待办、番茄钟和可拖动组件：通过同一个 store 修改状态，不再直接写旧配置键。
- 浏览器/Supabase 同步：通过相同的 capture/apply 入口；不再让 Supabase 模块先落盘、主页随后又写一次旧字段。

权威记录仍使用 `navinocode_advanced_state`，schema 升为 **5**，以区分 PR #3 的 v4 兼容投影模型。每个 `workspace.apps[]` 的网站只有一个 `folderId`，null 表示未分组；`folder.appIds` 只在迁移时读取，不保留为第二份关系表。

旧 `apps/todos/componentSettings/...` 只在升级时读取一次，此后保留原值作为回退依据，不再双向同步。为兼容旧导出格式，快照顶层字段是活动工作区的派生投影，并非另一份权威数据。应用切换、命令设置和同步应用无需整页 reload；场景切换会重置该场景的临时拖动/计时 UI。

## 迁移、删除和恢复

1. v3 同一网站曾加入多个文件夹时，确定性地选择第一个；显式 `folderId:null` 优先保留根归属。v4 已有目录结构直接归一化，不再用旧根应用缓存覆盖。
2. 迁移前保留 `navinocode_workspace_migration_backup`（原工作区 JSON、旧应用和场景设置，不含 Supabase 凭据）。备份或保存失败就停止，不假装成功。
3. 原始权威 JSON 损坏或版本过新时进入错误边界，提供导出原始恢复数据，不静默清空。旧 scalar JSON 损坏按类型回退；空应用数组和亮度 0 是合法状态。
4. 工作区、文件夹、网站、待办都有删除标记。新版本同步按实体 ID/时间戳合并，网站改 URL 不改变身份；旧版 URL 去重仍保留路径大小写。
5. 工作区名称、网站顺序和每项设置分开保存修改时间，减少“后来的无关修改覆盖较新的名称/设置”的风险。
6. 撤销保留已删除 ID 的标记，对恢复的实体分配新 ID；过期撤销直接拒绝。
7. 导入和实际应用不同的同步快照前保存 **一个最近恢复点** `navinocode_workspace_recovery`。恢复入口在“设置 → 数据”。恢复/文件导入为显式替换，给恢复的场景分配新 ID，保留被替换场景的删除标记，避免旧端复活它们。恢复点不是多版本历史。
8. compact 浏览器快照省略的本地图片按工作区恢复；明确空字符串仍表示清空。切换活动工作区不改变同步内容比较结果，另一设备查看不同场景不会仅因此触发同步。

## 本次增加的可用能力

跨工作区命令搜索（显示工作区/文件夹路径）、文件夹内添加网站、单项/多选移动、删除确认与撤销、导入/同步前最近恢复点、当前页面的原生同步成功/失败状态展示。保留图标编辑与 Dock 排序，不强迫用户通过两个不同编辑器操作。

尚未实现完整同步诊断历史/差异预览、多恢复点管理、跨工作区批量移动和标签页会话保存/恢复；不要把这些列为已完成。

## 明确的剩余边界

- 单个权威记录解决“多 key 半写”和同页陈旧副本回写，不等于跨标签页原子 read-modify-write。仍需跨页协调者或锁来解决真正同时操作的竞争。
- Supabase 仍为读 revision 后 upsert，未引入数据库 CAS/RPC；原生同步仍缺少跨设备事务/完整 generation 哈希。所有合并都不是分布式一致性的证明。
- 合并依赖设备时钟，删除优先且不回收 tombstone；长期规模和时钟偏差仍需后续方案。两端共同删除所有工作区会拒绝应用并提示冲突，而不是自动生成空状态掩盖问题。
- 旧版本客户端仍可写旧协议，无法保证混用版本不丢语义；建议所有设备升级后再开启同步。
- 当前自动同步提示仅提供基础反馈，不包含可审计的历史、逐项冲突选择、恢复差异预览。
